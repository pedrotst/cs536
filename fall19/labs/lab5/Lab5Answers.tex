\section*{Bonus Problem}
In order to implement the bonus problem we simply moved the order in which ACK happens.
Before we would ACK as soon as we are setting up a tunnel. Now we only ACK when we have reached the
router-k, then every time an overlaygopher receives an ACK it sends an ACK to the previous connection as well,
creating a domino effect until it reaches createoverlay.

Our tests indicates that it behaves as expected, i.e. if one of the overlay is not succeded, createoverlay
will never get an ACK. As of right now createoverlay simply hangs waiting indefinately for an answer. A good future enhancement
would be for createoverlay to retry after a few seconds and then give up after a while.

Another interesting problem is for v2 is that we do no tear down old sockets, even though we update the table.
This means that our server may have ghost connections and is still able to receive data from that port, although it would still
be sent to the right place because the forward table is still up.
